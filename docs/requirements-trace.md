# CampusFix 需求追踪与验收矩阵

> **建议仓库位置**：`docs/requirements-trace.md`  
> **版本**：V1.0（W1-D5 P0 冻结基线）
> **基线文件**：`docs/SRS.md`（W1-D5 冻结版，特别是第 44～56 章）
> **开发路线**：C++17 + Drogon REST API + Vue3 / Element Plus / Axios / ECharts + SQLite  
> **说明**：本文是**需求、计划及预期测试**，不是已经实现或执行过的测试报告。

## 0. 阅读方式与共同约束

- **P0**：必须实现并测试的 MVP；**P1**：有余力再实现；**P2**：本期不开发。
- 角色代码：`reporter`（报修人）、`worker`（维修人员）、`dispatcher`（调度管理员）、`sysadmin`（系统管理员）。所有敏感操作由后端按角色与资源范围校验。
- 工单状态码：`DRAFT`、`PENDING_REVIEW`、`PENDING_SUPPLEMENT`、`PENDING_DISPATCH`、`PENDING_ACCEPT`、`IN_PROGRESS`、`PENDING_VERIFY`、`COMPLETED`、`CLOSED`、`CANCELLED`。
- API 采用 `/api` 前缀，HTTP 状态码与业务码共同表达结果，分页结构为 `items/page/page_size/total`。
- 所有状态变化集中由 Service 层校验，关键变更及历史日志一起写入事务；前端不得直接决定实际操作者和目标状态。
- **验收用例均标记“待实现/待执行”**。需求追踪矩阵不应虚构代码存在或测试通过。
- TC 编号在本文每个 FR 的“预期验收”中定义唯一语义；其他文档只能引用，不得为同一编号另赋含义。

## 2. P0 逐项需求卡（13 项）

### FR-001 — 登录、退出、会话失效

- **发起角色**：未登录访客登录；已登录四角色用户退出或查询个人信息。
- **前置条件**：数据库已有处于启用状态的模拟用户；认证服务与会话存储可用。
- **触发和输入**：输入用户名/密码提交登录；携带有效 Token 请求 `/api/auth/me`；点击退出提交当前 Token。
- **正常结果**：验证安全哈希后发放随机会话 Token，返回用户身份及角色；`me` 获取本人信息；退出后服务端撤销会话。
- **异常/边界**：错误密码、禁用用户、空字段、过期/撤销 Token 不得取得受保护信息；不泄露密码哈希和明文 Token。
- **预期验收**：`TC-AUTH-01` 正确账号登录成功并返回自身角色；`TC-AUTH-02` 错误密码返回安全错误；`TC-AUTH-03` 退出后原 Token 访问受保护接口返回 401；`TC-AUTH-04` 过期 Token 被拒绝。

### FR-002 — 后端角色与资源鉴权

- **发起角色**：全部已认证角色。
- **前置条件**：存在不同报修人的工单、不同负责人的派单记录、不同辖区数据。
- **触发和输入**：调用工单详情、时间线、附件、调度、维修、评价及统计接口（使用路径中的真实资源 ID）。
- **正常结果**：`reporter` 仅能处理本人权限范围的数据，`worker` 只处理有效分配给本人的任务，`dispatcher` 按授权区域操作，`sysadmin` 具备定义好的系统管理权限。
- **异常/边界**：登录用户跨角色、跨工单、跨辖区访问返回 403 或避免泄露存在性的 404；前端隐藏按钮不代表授权。
- **预期验收**：`TC-SEC-01` 未登录拒绝；`TC-SEC-02` 报修人读取他人工单拒绝；`TC-SEC-03` 非负责人接单拒绝；`TC-SEC-04` 报修人调用审核/派单拒绝；`TC-SEC-05` 未授权附件/时间线/统计不可访问。

### FR-003 — 创建和提交工单

- **发起角色**：`reporter`，或以报修人身份创建本人报修的其他允许用户。
- **前置条件**：已登录；位置和故障分类是有效基础数据。
- **触发和输入**：填写标题、故障类别、位置、故障描述、申报紧急程度；通过 `POST /api/work-orders` 创建，再通过 `/submit` 提交。
- **正常结果**：服务端记录报修人而非信任前端传入的 `reporter_id`；创建时为 `DRAFT`，提交后为 `PENDING_REVIEW`；正式提交时生成或确认唯一工单号并记录状态日志。**是否提供可操作的“保存草稿”UI，见第 4 节决策项 Q-01。**
- **异常/边界**：缺少必填字段返回 400/422；不存在的分类/位置拒绝；重复提交应避免同一操作生成多份正式工单；已提交工单不可直接重复提交。
- **预期验收**：`TC-ORDER-01` 有效报修最终进入 `PENDING_REVIEW` 且单号唯一；`TC-ORDER-02` 缺少描述或位置被拒绝；`TC-ORDER-03` 重复提交不能创建重复的有效工单。

### FR-004 — 工单列表、详情与时间线

- **发起角色**：全部已认证角色，在各自数据授权范围内访问。
- **前置条件**：已有不同状态和不同报修人的模拟工单及状态变更记录。
- **触发和输入**：`GET /api/work-orders` 的页码、状态/类别筛选；`GET /api/work-orders/{id}` 与 `GET /api/work-orders/{id}/timeline`。
- **正常结果**：列表按角色范围过滤并分页；详情返回有效负责人、状态、公开时间线和有权限的附件元信息；当前维修员可在 `IN_PROGRESS` 追加一次到场事件和多次进度事件；内部备注不向普通报修人泄露。
- **异常/边界**：空列表正常返回空数组、合法分页；越权或不存在的工单拒绝；非法页码/筛选条件被校验。
- **预期验收**：`TC-ORDER-04` 本人列表只含本人工单；`TC-ORDER-05` 正确展示当前状态和历史时间线；`TC-ORDER-06` 未授权详情/内部备注无法访问；`TC-PROG-01` 当前负责人每个派单只能记录一次到场；`TC-PROG-02` 当前负责人可追加进度且状态不变；`TC-PROG-03` 非负责人、错误状态或重复到场被拒绝且不产生日志。

### FR-005 — 审核与退回补充

- **发起角色**：授权区域的 `dispatcher`。
- **前置条件**：工单处于 `PENDING_REVIEW`；服务端已确认调度员权限。
- **触发和输入**：审核通过并确认类别/紧急程度；或退回/拒绝并填写原因；报修人在 `PENDING_SUPPLEMENT` 时补充后再次提交。
- **正常结果**：通过 → `PENDING_DISPATCH`；退回 → `PENDING_SUPPLEMENT`；补充再提交 → `PENDING_REVIEW`；拒绝无效工单 → `CANCELLED`；全部记录操作人和原因。
- **异常/边界**：退回无原因、审核已处理的工单、非授权管理员操作被拒绝；原工单编号和历史记录不丢失。
- **预期验收**：`TC-WF-01` 审核通过状态变化正确；`TC-WF-02` 退回原因必填且可重新提交；`TC-WF-03` 越权审核或非法状态审核失败且没有写入错误状态。

### FR-006 — 维修人员技能与负载管理

- **发起角色**：`dispatcher` 按辖区管理；`sysadmin` 仅在显式取得 `WORKER_MANAGE` 及对应范围时管理。
- **前置条件**：已存在用户、技能、维修人员档案与管理区域基础数据。
- **触发和输入**：查询/修改人员技能与熟练度、资格状态、服务区域、在岗状态、最大并行任务数。
- **正常结果**：保存有效人员档案；调度所用实时负载来自数据库当前有效派单；技能熟练度为 1～5，最大容量必须大于 0 才能接单。
- **异常/边界**：不存在的技能、负数容量、非法熟练度、越权修改被拒绝；达到容量的人员不能参加新工单的普通推荐。
- **预期验收**：`TC-WORKER-01` 合法档案与技能修改成功；`TC-WORKER-02` 非法负载/技能被拒绝；`TC-WORKER-03` 已满负载人员不可作为合格候选。

### FR-007 — 智能调度筛选与推荐评分

- **发起角色**：`dispatcher`。
- **前置条件**：工单处于 `PENDING_DISPATCH`；已有技能/区域/在岗与任务负载数据。
- **触发和输入**：`GET /api/work-orders/{id}/dispatch-candidates`；输入源为工单属性与当前人员状态，不允许客户端伪造得分。
- **正常结果**：先排除无技能/资格、不可用、无区域授权、超负载人员；再计算技能 35%、区域 20%、空闲程度 20%、历史效率 10%、评价 10%、紧急值班 5% 的归一化分数；返回前三名及其他合格人员、分项分数、理由与风险。历史效率样本为最近 20 个正常完成派单，单样本分 `clamp(100×类别目标分钟/接单至最终结果提交分钟,0,100)`；历史评价为最近 20 个最终完成工单的 `平均星级×20`。两项分别在有效样本少于 3 时取 60，否则算术平均并四舍五入到 1 位小数。
- **异常/边界**：无候选时返回空数组和排除原因，不能擅自放宽硬约束；同分按低负载、低人员编号排序；**推荐操作只读、不创建派单**。
- **预期验收**：`TC-DSP-01` 技能剔除；`TC-DSP-02` 资质剔除；`TC-DSP-03` 无法接单剔除；`TC-DSP-04` 满负载剔除；`TC-DSP-05` 固定权重总分核对；`TC-DSP-06` Top 3、其他合格候选与解释正确；`TC-DSP-07` 同分按低负载、低人员 ID 稳定排序；`TC-DSP-08` 无候选返回解释且状态不变；`TC-DSP-09` 历史效率按目标时间、最终返工提交时间及最近 20 样本可复现；`TC-DSP-10` 少于 3 样本取 60，评价星级正确归一到 0～100。

### FR-008 — 派单、接单、拒单与转派

W7-D2 D-021补充：API-34按本人身份或DISPATCH授权范围查询真实转派申请；不从历史时间线推断可审批状态、不扩大详情权限。TC-WF-08/09关联新增查询与HTTP测试，覆盖本人历史、当前有效PENDING队列、独立能力、跨区/撤销/重叠授权、当前版本及只读无写入；不是新增FR。

- **发起角色**：`dispatcher` 确认派单/审批转派；当前有效 `worker` 接单、拒单或申请转派。
- **前置条件**：派单时工单为 `PENDING_DISPATCH`，人员合格且未满载；接单/拒单时工单为 `PENDING_ACCEPT` 且操作人是当前负责人。
- **触发和输入**：管理员发送 `worker_id`、原因（必要时）、`expected_version`；维修人员接单或填写拒单原因；维修人员申请转派后由管理员审批。
- **正常结果**：推荐预览不落库；确认派单时重新计算并原子保存最终权重/候选依据/选中人员快照。可选择任一合格候选，选择非 Top 3 时理由必填。派单 → `PENDING_ACCEPT`；接单 → `IN_PROGRESS`；拒单 → `PENDING_DISPATCH`，原有效派单失效；批准维修员转派申请 → `PENDING_DISPATCH` 并留存历史。
- **异常/边界**：重复派单、非负责人接单、无理由拒单、无资质/超负载人工派单均不得成功；P0 不允许管理员在没有待处理维修员申请时主动改派，该能力列入 P1。
- **预期验收**：`TC-WF-04` 合规派单成功并保存最终推荐快照；`TC-WF-05` 本人接单成功；`TC-WF-06` 非负责人接单失败；`TC-WF-07` 拒单后回待派单并释放负载；`TC-WF-08` 维修员申请及管理员审批记录可追溯；`TC-WF-09` 无待处理申请的管理员主动改派被拒绝。

### FR-009 — 维修提交、返工和验收

- **发起角色**：当前有效 `worker` 提交结果；原报修人验收（主要角色 reporter 或 worker，且数据库 reporter_id 等于认证用户 ID；D-017 勘误）。
- **前置条件**：维修提交前工单为 `IN_PROGRESS`；验收前为 `PENDING_VERIFY`。
- **触发和输入**：维修员填写 `repair_summary` 后提交；报修人提交 `approved=true/false`，未通过时填写 `reason`。
- **正常结果**：提交结果 → `PENDING_VERIFY`，并在同一事务将未决转派申请改为 `SUPERSEDED`；通过 → `COMPLETED`，同时以 `COMPLETED` 结束有效派单并释放负载；不通过 → `IN_PROGRESS`，返工次数增加，保留当前负责人和旧结果/原因。
- **异常/边界**：空维修说明、非负责人提交、非原报修人验收、无理由拒绝验收均失败，状态和历史不被破坏。
- **预期验收**：`TC-WF-10` 维修提交成功、记录最终提交时间并将未决转派申请原子标记为 `SUPERSEDED`；`TC-WF-11` 验收通过并原子结束派单/释放负载；`TC-WF-12` 验收失败返回处理中并记录原因；`TC-WF-13` 非法操作或重复提交被拒绝。

### FR-010 — 评价、关闭与不可变历史

- **发起角色**：原报修人评价（主要角色 reporter 或 worker，且数据库 reporter_id 等于认证用户 ID；D-017 勘误）；授权 `dispatcher` 归档关闭。
- **前置条件**：评价时为 `COMPLETED`；关闭时为 `COMPLETED` 且符合归档策略；历史事件已有操作人和时间。
- **触发和输入**：报修人填写 1～5 分及可选评价文字；调度员执行关闭。
- **正常结果**：同一工单最多保存一次有效评价；归档后状态为 `CLOSED`；整个生命周期历史按追加方式保留，不可通过普通编辑覆盖。
- **异常/边界**：重复评价、评分超范围、未完成工单评价、关闭后新增评价或更改主体信息均失败；允许未评价的 `COMPLETED` 工单直接关闭。
- **预期验收**：`TC-WF-14` 首次评价成功且 1～5 分限制有效；`TC-WF-15` 重复评价被数据库约束与服务层拒绝；`TC-WF-16` 关闭后工单不可编辑但历史仍可授权查询。

D-017 补充验收（FR-009/010，W3-D4 先验证 Policy；不代表 API-24/25 已实现）：reporter/worker 可以验收本人报修；worker 可以对本人报修返工及在 COMPLETED 时评价；对他人报修，即使 worker 是当前负责人也不得验收/评价；sysadmin 管理授权不授予原报修人身份；本人操作仍须校验状态、版本和评价唯一性。

### FR-011 — 图片上传与授权下载

- **发起角色**：有权访问/修改关联工单的 `reporter` 或 `worker`；管理员按权限访问。
- **前置条件**：用户已认证且对该工单具备相应权限，存在有效工单记录。
- **触发和输入**：上传 JPG/JPEG/PNG/WEBP 图片；报修现场图 `REPORT` 与维修完成图 `REPAIR_RESULT` 分别最多 3 张，每张不超过 5 MiB；下载按附件 ID 查询。
- **正常结果**：服务器检验文件实际类型、大小、数量并安全命名，保存元数据；取得合法授权后才能读取文件内容。
- **异常/边界**：类型伪装、超大小/数量、路径穿越、非授权附件访问均失败；写文件与数据库记录失败应有回滚或清理机制。
- **预期验收**：`TC-FILE-01` 合法图片可上传/查看；`TC-FILE-02` REPORT 与 REPAIR_RESULT 各 3 张可共存，各自第 4 张或单张超 5 MiB 被拒；`TC-FILE-03` 非图片与危险路径被拒；`TC-FILE-04` 非授权附件下载被拒。

### FR-012 — 看板与基础统计

- **发起角色**：`dispatcher`、`sysadmin`（以各自授权数据范围统计）。
- **前置条件**：数据库包含覆盖多状态、多类别、不同维修人员的模拟工单。
- **触发和输入**：`GET /api/dashboard/summary`，可选时间范围/授权区域，前端展示 ECharts 或汇总卡片。
- **正常结果**：返回待审核、待派单、处理中、已完成等数量，以及类别分布、人员负载和完成率；完成率以 `submitted_at` 落在查询区间的固定工单队列为分母，其中当前状态为 `COMPLETED` 或 `CLOSED` 的数量为分子；查询结果与数据库同一统计口径一致。
- **异常/边界**：无数据时正确展示零值和空图；不得泄漏跨区域统计；分母为零时完成率有明确定义。
- **预期验收**：`TC-STAT-01` 状态数量与准备数据一致；`TC-STAT-02` 按权限区域统计正确；`TC-STAT-03` 空数据与零分母页面不崩溃。

### FR-013 — 并发派单一致性

- **发起角色**：系统后端（可能由多个调度员同时触发）。
- **前置条件**：单张工单处于 `PENDING_DISPATCH`；两个并发请求使用同一旧版 `expected_version`；维修人员的剩余容量有限。
- **触发和输入**：两次并发 `POST /api/work-orders/{id}/assign`。
- **正常结果**：只有一个请求成功；其他请求收到 HTTP 409；同一工单最多一个有效派单，工单状态/版本、人员容量及日志一致。
- **异常/边界**：数据库忙、事务中断、人员已被其他工单占满时全部回滚，不允许出现“工单已派但没有有效派单记录”等半完成状态。
- **预期验收**：`TC-CON-01` 并发同工单仅一次成功；`TC-CON-02` 负载上限不会被并发突破；`TC-CON-03` 事务失败没有部分写入数据。

- **角色/前置**：调度管理员配置班次及响应时限，维修员存在状态与工单截止时间。
