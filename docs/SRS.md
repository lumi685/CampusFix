# 1. 项目概述

## 1.1 项目名称

**基于 C++ 的校园维修工单与智能调度系统**

英文名称：

**CampusFix——Campus Maintenance Work Order and Intelligent Dispatch System**

## 1.2 项目背景

高校宿舍、教学楼、实验楼和公共区域中存在大量日常维修需求，例如水电故障、门窗损坏、网络异常、家具损坏和公共设施故障。传统报修流程通常依赖电话、纸质登记或即时通信工具，容易出现以下问题：

1. 报修信息格式不统一，故障位置、现象和图片等关键信息容易缺失；
2. 工单主要依靠管理员人工分配，难以同时兼顾技能匹配、紧急程度和人员负载；
3. 报修人无法及时了解受理、派单、维修和验收进度；
4. 紧急故障与普通故障混在同一队列中，响应优先级不明确；
5. 维修人员的技能、工作状态和历史任务缺少统一管理；
6. 工单处理过程缺少完整留痕，出现争议时难以追溯；
7. 管理部门难以通过数据分析发现高频故障、重点区域和人员负载问题。

因此，本项目拟建设一套面向校园场景的维修工单管理与智能调度平台。学生或教师可在线提交报修申请，管理员维护维修人员、技能和排班信息，系统根据故障类型、紧急程度、技能匹配度、当前任务量等因素推荐负责人，并对工单全生命周期进行跟踪、评价和统计分析。

## 1.3 项目定位

本项目不是简单的报修登记页面，而是一个具有完整业务闭环的校园维修管理系统。系统应形成以下处理链路：

> **用户报修 → 信息校验 → 工单受理 → 智能调度 → 人工确认 → 维修处理 → 进度反馈 → 用户验收 → 服务评价 → 数据统计**

# 2. 项目建设目标

## 2.1 业务目标

系统应实现：

- 统一校园报修入口，规范故障信息采集；
- 建立从提交到归档的工单生命周期；
- 根据多种因素推荐合适的维修人员；
- 为紧急故障提供更高的调度和响应优先级；
- 向报修人透明展示维修进度；
- 为维修人员提供清晰的任务工作台；
- 为管理员提供调度看板、统计报表和过程追溯能力。

## 2.2 技术目标

掌握并综合应用：

- C++ 面向对象程序设计；
- C++ STL、智能指针和异常处理；
- Drogon Web 框架；
- REST API 与 JSON 数据交换；
- 策略模式和模块化软件设计；
- 优先队列与加权评分算法；
- C++ 多线程、并发控制和异步任务；
- 数据库设计与事务处理；
- 文件上传、存储和访问控制；
- Token 身份认证与多角色权限控制；
- Vue3、Element Plus、Axios 和 ECharts；
- 日志、测试和部署。

## 2.3 工程目标

培养将业务问题转化为可运行软件系统的能力，使项目覆盖：

> **需求分析 → 系统设计 → 数据库设计 → C++ 后端开发 → 前端开发 → 调度算法实现 → 测试 → 部署**

## 2.4 产品目标

最终形成一个可独立运行的校园维修管理平台，能够：

- 支持多角色登录和权限隔离；
- 支持文字与图片报修；
- 支持工单查询、筛选、分配、转派和关闭；
- 自动计算维修人员推荐结果；
- 展示工单处理进度和操作记录；
- 支持服务评价和异常申诉；
- 提供工作量、响应时长、完成率等统计指标。

# 3. 项目应用场景

## 3.1 学生宿舍报修

适用于宿舍内照明、插座、水龙头、门锁、家具、空调和网络等故障。学生提交宿舍楼、房间号、故障描述和现场图片后，系统生成工单并推荐维修人员。

## 3.2 教学楼与实验楼报修

适用于教室照明、多媒体设备、门窗、给排水和实验室公共设施故障。紧急故障可由报修人申报，最终紧急等级由管理员确认。

## 3.3 校园公共区域巡检报修

保卫、物业或后勤人员在巡检过程中发现道路照明、消防设施、公共卫生间和其他公共设施故障时，可直接创建工单并指定位置。

## 3.4 后勤调度管理

管理员通过调度看板查看待分配工单、超时工单、人员负载和紧急任务，采用系统推荐或人工方式完成派单和转派。

## 3.5 维修人员移动工作台

维修人员查看个人待办任务，接受工单、更新进度、填写维修结果、上传处理后图片，并在无法处理时提交转派或协助申请。

# 4. 系统用户与权限

系统主要包含四类用户。

| 用户角色 | 主要职责 | 核心权限 |
| --- | --- | --- |
| 学生或教师 | 提交报修、查看进度、补充信息、确认完成、服务评价 | 仅访问本人提交或被授权查看的工单 |
| 维修人员 | 接收任务、更新进度、填写处理结果、申请转派；可本人报修 | 访问当前/受控历史分配给本人及本人报修的工单 |
| 调度管理员 | 审核工单、维护基础数据、确认或调整派单、处理异常 | 查看辖区工单并执行调度管理 |
| 系统管理员 | 系统身份；P0 业务访问须显式能力与数据范围授权 | 不天然拥有审核、派单、维修、验收等业务权限；通用管理后台为 P1 |

权限控制采用基于角色的访问控制模型。后端必须对每个受保护接口进行身份认证和权限校验，前端菜单隐藏不能替代后端鉴权。

# 7. 核心业务流程

## 7.1 标准报修流程

```text
用户填写报修信息
        ↓
系统校验并创建工单
        ↓
管理员审核工单有效性
        ↓
系统生成调度推荐结果
        ↓
管理员确认派单（可选择其他合格候选）
        ↓
维修人员接单并开始处理
        ↓
维修人员提交维修结果
        ↓
报修人验收（可在关闭前评价）
        ↓
工单关闭并进入统计分析
```

## 7.2 紧急工单流程

紧急工单提交后，应进入高优先级队列。系统立即计算推荐人员并在调度看板突出显示。管理员确认后优先派单；若超过规定时间仍未处理，系统应生成超时标记并记录升级事件。

## 7.3 退回与补充流程

当位置、图片或故障描述不足时，管理员可以退回工单并说明原因。报修人补充信息后重新提交，系统保留原始内容和全部修改记录。

## 7.4 转派流程

当维修人员缺少所需技能、临时离岗或现场情况与申报不符时，可发起转派申请。管理员审核后重新执行调度，原负责人、转派原因和新负责人均应写入操作日志。

# 8. 工单状态模型

## 8.1 工单状态

| 状态 | 含义 |
| --- | --- |
| 草稿 | 用户暂存但尚未提交 |
| 待审核 | 工单已提交，等待管理员检查 |
| 待补充 | 信息不完整，等待报修人修改 |
| 待派单 | 审核通过，等待确定负责人 |
| 待接单 | 已派给维修人员，等待确认接收 |
| 处理中 | 维修人员已开始处理 |
| 待验收 | 维修人员已提交结果，等待报修人确认 |
| 已完成 | 报修人验收通过或系统按规则自动完成 |
| 已关闭 | 工单流程结束并归档 |
| 已取消 | 工单在允许条件下被取消 |

## 8.2 状态转换规则

1. 只有草稿和待补充状态允许报修人修改主要报修信息；
2. 待审核工单只能由调度管理员审核、退回或取消；
3. 待派单工单完成派单后进入待接单状态；
4. 维修人员接单后进入处理中状态；
5. 维修人员提交结果后进入待验收状态；
6. 报修人验收通过后进入已完成状态；
7. 验收不通过时，可退回处理中状态并填写原因；应保留同一工单与负责人并记录返工次数；
8. 已关闭和已取消状态在 P0 中均为终态，不能恢复或删除历史；确需重新维修时应创建关联的新工单；
9. 每次状态变化必须记录操作者、时间、前后状态、备注和关联附件。
10. 已完成工单评价后可关闭；未评价工单由管理员按规则归档关闭。自动验收与定时自动关闭不属于 P0，见第 46 章。
11. 拒单、转派、撤销派单的准确状态与日志规则以第 46 章的转换表为准。

# 9. 用户认证与账户管理

## 9.1 登录认证

系统应支持：

- 用户名和密码登录；
- Token 签发、校验和失效；
- 退出登录；
- 登录失败次数限制；
- 密码加密存储；
- 获取当前用户资料和权限列表。

课程项目阶段可采用 JWT 或服务端 Token。密码不得以明文形式存储。

## 9.2 用户管理

系统管理员可以：

- 新增、编辑、禁用和启用用户；
- 分配用户角色；
- 重置用户密码；
- 查询用户状态；
- 查看用户最近登录时间。

## 9.3 数据访问范围

- 普通用户只能查看本人创建的工单；
- 维修人员只能查看本人或被授权班组的任务；
- 调度管理员按管理区域查看工单；
- 系统管理员可查看全校数据。

# 10. 报修申请模块

## 10.1 功能描述

学生或教师通过统一表单提交故障信息。P0 应提供必填校验、图片预览、后端 `DRAFT` 与显式提交；复杂草稿自动保存、版本恢复及独立草稿工作台属于 P1。

## 10.2 报修字段

| 字段 | 说明 | 是否必填 |
| --- | --- | --- |
| 报修标题 | 简要描述故障 | 是 |
| 故障类别 | 水电、门窗、网络、家具等 | 是 |
| 故障位置 | 校区、楼宇、楼层、房间或区域 | 是 |
| 故障描述 | 详细说明现象和影响 | 是 |
| 期望上门时间 | 便于协调维修时间 | 否 |
| 申报紧急程度 | 普通、较急、紧急 | 是 |
| 联系人 | 现场联系人 | 是 |
| 联系方式 | 用于维修沟通 | 是 |
| 现场图片 | 故障现场附件 | 否 |

## 10.3 功能要求

系统应支持：

1. 新建后端草稿，并由用户显式提交；
2. 提交报修并生成唯一工单编号；
3. 上传、预览和删除附件；
4. 校验字段长度、文件类型和文件大小；
5. 自动记录报修人和提交时间；
6. 在允许的状态下撤回或取消工单；
7. 复制历史工单内容快速发起类似报修（P1）；
8. 短时间重复报修提醒（P1）；P0 仍通过版本和状态校验防止同一草稿重复提交。

## 10.4 工单编号

建议采用以下编号格式：

```text
WX + 日期 + 当日流水号

示例：WX202610100001
```

编号必须全局唯一，生成过程应保证并发安全。P0 在草稿首次执行 `DRAFT → PENDING_REVIEW` 时于同一事务生成；草稿的 `order_no` 为 NULL，待补充再提交保留原编号。

# 11. 工单审核与管理模块

## 11.1 工单审核

调度管理员应能：

- 查看待审核工单；
- 确认或调整故障分类；
- 确认实际紧急等级；
- 修改管理区域和责任班组；
- 审核通过并进入调度；
- 退回报修人补充信息；
- 将重复、无效或不属于维修范围的工单关闭。

## 11.2 工单查询

支持按以下条件组合查询：

- 工单编号；
- 报修人；
- 故障类别；
- 校区、楼宇和房间；
- 工单状态；
- 紧急程度；
- 维修人员；
- 提交时间和完成时间；
- 是否超时。

查询结果应支持分页、排序和导出。课程项目可将导出功能作为进阶功能。

## 11.3 工单操作

管理员应能执行：

- 派单；
- 改派；
- 调整优先级；
- 添加内部备注；
- 延期并填写原因；
- 关闭异常工单；
- 查看完整操作时间线。

# 12. 故障分类与位置管理

## 12.1 故障分类

系统应支持多级故障分类，例如：

```text
水电维修
├── 照明故障
├── 插座故障
├── 漏水
└── 排水堵塞

设施维修
├── 门锁
├── 门窗
├── 家具
└── 公共设施

网络与设备
├── 校园网络
├── 多媒体设备
└── 其他弱电设备
```

每个故障类别可以关联：

- 默认紧急程度；
- 所需技能标签；
- 标准响应时限；
- 标准完成时限；
- 默认责任班组。

## 12.2 校园位置

位置数据建议采用以下层级：

```text
校区 → 建筑 → 楼层 → 房间或公共区域
```

管理员可以新增、修改、启用或停用位置。已经被工单引用的位置不得直接物理删除。

# 13. 维修人员与技能管理

## 13.1 维修人员信息

维修人员档案至少包括：

| 字段 | 说明 |
| --- | --- |
| 人员编号 | 唯一编号 |
| 姓名 | 维修人员姓名 |
| 所属班组 | 水电、网络、综合维修等 |
| 技能标签 | 可处理的故障类别及熟练度 |
| 服务区域 | 负责的校区或楼宇 |
| 联系方式 | 工作联系方式 |
| 在岗状态 | 在岗、忙碌、休息、请假、停用 |
| 最大并行任务数 | 可同时处理的工单上限 |
| 当前任务量 | 未完成工单数量或工作量 |
| 历史评分 | 已完成工单的评价均值 |

## 13.2 技能模型

每名维修人员可关联多个技能。技能关系应至少包含：

- 技能类型；
- 熟练度；
- 是否持有必要资质；
- 生效时间；
- 状态。

熟练度可设置为 1～5 级，用于调度评分。

## 13.3 排班与可用状态

系统应支持：

- 配置人员工作时段；
- 标记请假、离岗和临时不可用；
- 自动统计当前未完成任务；
- 判断人员是否达到最大任务量；
- 为紧急值班人员设置特殊标签。

# 14. 智能调度模块

## 14.1 功能目标

智能调度模块根据工单属性和维修人员状态生成候选人排序，为管理员提供推荐结果。系统推荐不直接取代管理人员决策，管理员可以确认推荐结果，也可以人工选择负责人并填写调整原因。

## 14.2 调度输入

工单侧输入包括：

- 故障类别；
- 所需技能；
- 紧急程度；
- 故障位置；
- 提交时间；
- 期望上门时间；
- 标准响应时限；
- 是否需要特殊资质。

人员侧输入包括：

- 技能匹配情况；
- 熟练度；
- 服务区域；
- 当前任务量；
- 最大并行任务数；
- 在岗和排班状态；
- 历史完成效率；
- 历史服务评分；
- 是否为紧急值班人员。

## 14.3 调度处理流程

```text
读取待派工单
      ↓
检查工单完整性
      ↓
执行硬性条件筛选
      ↓
计算候选人员各项得分
      ↓
按权重计算综合得分
      ↓
生成候选人排序与推荐理由
      ↓
管理员确认或人工调整
      ↓
写入调度结果和审计日志
```

## 14.4 硬性筛选条件

候选人员必须满足：

1. 账户和人员状态有效；
2. 当前处于可接单状态；
3. 具备工单要求的必要技能或资质；
4. 当前任务量未超过上限；
5. 服务区域符合要求，或允许跨区域支援；
6. 排班时间满足工单期望处理时间。

不满足硬性条件的人员不得仅因综合得分较高而进入首选推荐。

## 14.5 加权评分模型

建议采用归一化后的加权评分：

```text
总分 = 技能匹配分 × Ws
     + 区域匹配分 × Wa
     + 空闲程度分 × Wl
     + 历史效率分 × We
     + 服务评价分 × Wr
     + 紧急值班加分 × Wu
```

建议初始权重如下：

| 评分因素 | 建议权重 |
| --- | ---: |
| 技能匹配 | 35% |
| 区域匹配 | 20% |
| 空闲程度 | 20% |
| 历史效率 | 10% |
| 服务评价 | 10% |
| 紧急值班 | 5% |

P0 固定上述权重；动态配置属于 P1。推荐预览不写业务记录，确认派单时才保存最终重算后的权重与候选依据快照，避免历史结果无法解释。

## 14.6 工单优先级

待调度工单使用优先队列组织。优先级可根据以下因素确定：

```text
工单优先级 = 紧急程度基础分
           + 等待时长加分
           + 超时风险加分
           + 影响范围加分
```

当优先级相同时，提交时间更早的工单优先处理。紧急程度由管理员最终确认，防止普通用户滥用紧急标记。

## 14.7 推荐结果

系统应向管理员展示排名靠前的候选人员，并显示：

- 综合得分；
- 各评分项明细；
- 当前任务量；
- 匹配技能；
- 服务区域；
- 推荐理由；
- 可能的风险提示。

示例：

```json
{
  "worker_id": 18,
  "worker_name": "维修员A",
  "total_score": 90.5,
  "score_detail": {
    "skill": 95,
    "area": 100,
    "load": 75,
    "efficiency": 82,
    "rating": 90,
    "emergency_duty": 100
  },
  "reason": "技能匹配度高，负责当前区域，当前有1个未完成工单"
}
```

## 14.8 调度策略扩展

后端应采用策略模式封装调度算法，例如：

```cpp
class DispatchStrategy
{
public:
    virtual std::vector<DispatchCandidate> recommend(
        const WorkOrder& order,
        const std::vector<Worker>& workers
    ) const = 0;

    virtual ~DispatchStrategy() = default;
};
```

可实现以下策略：

- WeightedScoreStrategy：加权评分策略；
- LeastLoadStrategy：最小负载策略；
- SkillFirstStrategy：技能优先策略；
- EmergencyStrategy：紧急工单策略。

系统应允许根据工单类型选择策略，为后续替换或组合算法预留接口。

## 14.9 异常与兜底规则

当没有合格候选人时，系统应：

1. 明确提示无可用人员；
2. 说明被排除的主要原因；
3. 推荐责任班组或值班管理员；
4. P0 可从系统返回的其他合格候选中人工选择，选择非 Top 3 必须填写原因；跨区域人员只有已满足区域硬约束时才可选择，且**不得突破资质或最大并行任务数**；
5. 要求记录人工派单原因；
6. 对紧急工单产生待升级提醒。

# 17. 服务验收与评价模块

## 17.1 工单验收

维修人员提交处理结果后，报修人可以：

- 查看维修说明和处理后图片；
- 确认维修完成；
- 选择未解决并填写原因；
- 在规定时间内提交评价。

超过验收期限仍未操作时，可由系统按配置自动完成，但必须在时间线中标记为“系统自动验收”。**该功能在 V1.1 中划入 P2，P0 不启用，以避免未经确认就把维修结果视为通过。**

## 17.2 服务评价

P0 评价仅包含 `score`（1～5 的单项总评分）和可选 `comment`。同一工单只能提交一次有效评价，评价不改变 `COMPLETED` 状态；工单进入 `CLOSED` 后不接受新评价。多维评分、匿名展示、评价修改审批均属于 P1。

## 17.3 低分处理

低分自动复核属于 P1，不进入 P0 页面、接口或数据模型。

# 40. 项目建设原则

## 原则一：以真实维修流程为主线

所有功能围绕报修、调度、维修、验收和评价展开，避免形成彼此孤立的页面或接口。

## 原则二：以 C++ 工程能力为核心

重点体现 C++ 在面向对象、STL、策略模式、并发控制、资源管理和高性能后端开发方面的应用。

## 原则三：调度结果可解释

系统不仅给出推荐人员，还应说明候选人的评分构成和推荐原因，使管理员能够判断并修正调度结果。

## 原则四：自动推荐与人工决策结合

调度算法用于提升效率，但不能忽略现实中的临时离岗、特殊资质和现场协调等因素。人工调整必须保留原因和记录。

## 原则五：数据完整且过程可追溯

工单状态、负责人、处理记录、附件、评价和调度依据均应能够追溯。

## 原则六：模块化与可扩展

后续增加新的故障类别、调度策略、通知方式、存储方案或校园区域时，不应大规模修改原有系统。

# 46. 状态机与详细业务规则（新增，优先级高）

## 46.1 状态编码

使用固定英文状态码存储，中文文案只在前端映射：

`DRAFT` 草稿；`PENDING_REVIEW` 待审核；`PENDING_SUPPLEMENT` 待补充；`PENDING_DISPATCH` 待派单；`PENDING_ACCEPT` 待接单；`IN_PROGRESS` 处理中；`PENDING_VERIFY` 待验收；`COMPLETED` 已完成；`CLOSED` 已关闭；`CANCELLED` 已取消。

> “已到场”“维修进度 xx%”“已接单”不增加为独立工单状态；其中接单将工单切为 IN_PROGRESS，到场作为时间线事件。避免工单状态膨胀。

## 46.2 合法转换表

| 当前状态 | 操作/操作者 | 目标状态 | 必要条件、留痕 |
|---|---|---|---|
| DRAFT | 提交 / 报修人 | PENDING_REVIEW | 必填字段通过校验、工单号唯一 |
| PENDING_REVIEW | 审核通过 / 调度员 | PENDING_DISPATCH | 审核人、最终分类与紧急程度入库 |
| PENDING_REVIEW | 退回补充 / 调度员 | PENDING_SUPPLEMENT | 必须填写具体退回原因 |
| PENDING_SUPPLEMENT | 再提交 / 原报修人 | PENDING_REVIEW | 保留原工单号和修改历史 |
| DRAFT、PENDING_REVIEW、PENDING_SUPPLEMENT | 取消 / 原报修人或授权管理员 | CANCELLED | DRAFT 原因可选；已提交工单原因必填；不物理删除 |
| PENDING_DISPATCH | 派单 / 调度员 | PENDING_ACCEPT | 负责人符合技能、区域、在岗及容量硬约束 |
| PENDING_ACCEPT | 接单 / 当前维修员 | IN_PROGRESS | 只能本人接，记录接单时间 |
| PENDING_ACCEPT | 拒单 / 当前维修员 | PENDING_DISPATCH | 必填原因，关闭当前有效派单记录 |
| PENDING_ACCEPT、IN_PROGRESS | 维修员申请转派 + 管理员批准 | PENDING_DISPATCH | 原派单结束、释放负载、记录原因，再重新推荐；无申请主动改派为 P1 |
| IN_PROGRESS | 提交维修结果 / 当前维修员 | PENDING_VERIFY | 完成说明必填；记录该派单最终结果时间；未决转派申请同事务变为 SUPERSEDED |
| PENDING_VERIFY | 验收通过 / 原报修人 | COMPLETED | 记录验收；有效派单以 COMPLETED 结束并在同一事务释放负载 |
| PENDING_VERIFY | 验收不通过 / 原报修人 | IN_PROGRESS | 说明原因，返工计数 +1，保留当前负责人 |
| COMPLETED | 评价 / 原报修人 | COMPLETED | 一张工单仅一次有效评价 |
| COMPLETED | 归档关闭 / 授权调度管理员 | CLOSED | 记录关闭人和关闭时间；评价不是前置条件 |
| PENDING_DISPATCH | 取消 / 调度员 | CANCELLED | 必须说明原因 |

**禁止**：客户端任意提交目标状态；跨越中间状态；对 CLOSED/CANCELLED 修改主体数据；重复接单、重复派单、重复评价。所有转换在服务层集中校验并以事务持久化。审核/派单/关闭等受保护操作须检查角色及数据范围。流程中“补充材料”只能由原报修人操作。

## 46.3 五个关键异常

1. **无候选人**：返回空推荐与每类排除原因；工单保持待派单；不能为了填满列表绕过资质。
2. **维修人员拒单**：记录拒单理由、失效原分配、释放负载、回到待派单，不自动跳过审核。
3. **同一工单重复派单**：只有一次分配成功；后到请求返回业务冲突；数据库保持唯一有效负责人。
4. **验收不通过**：工单返工、保留前次结果与原因；不得覆盖历史时间线。
5. **人工选择与改派**：初次派单可选择其他合格人员，选择非 Top 3 时理由必填；P0 改派仅审批维修员申请，管理员无申请主动改派属于 P1；任何路径都不得绕过硬约束。

## 46.4 自动验收与紧急故障

P0 **不设置超时自动验收**，否则可能将未修复故障错误标记完成。紧急工单先由管理员确认优先级，调度推荐排序向其倾斜；重大漏电、消防等安全风险应展示“先现场安全处置并联系学校应急值班渠道”提示，不承诺系统替代现场应急流程。P1 加入超时提醒而非自动消除安全流程。

# 48. 数据模型与一致性约束（新增）

## 48.1 P0 表清单

P0 固定 16 张表：`users`、`auth_sessions`、`management_grants`、`locations`、`skills`、`fault_categories`、`workers`、`worker_skills`、`order_number_sequences`、`work_orders`、`attachments`、`assignments`、`transfer_requests`、`status_logs`、`dispatch_records`、`evaluations`。完整字段、类型、外键、删除策略和索引以 `database-design.md` 为唯一物理设计基线。

关键约束包括：用户名与 Token 哈希唯一；管理能力码受枚举检查；`fault_categories.target_completion_minutes > 0`；草稿单号可空、正式单号唯一；同工单最多一个 `ended_at IS NULL` 的有效派单；到场日志对每个 `assignment_id` 最多一条；每单一次评价；报修与维修结果附件分别最多 3 张（服务层计数并在事务内校验）。P1 再增加通知、排班和动态策略配置等模型。

## 48.2 一致性与事务

- **生成单号**：`WXYYYYMMDDNNNN`；首次提交时在事务内更新 `order_number_sequences` 并创建唯一编号；禁止简单“先查最大号再加 1”。
- **派单**：使用短 `BEGIN IMMEDIATE`，重新读取工单版本、人员硬约束和实时负载，重算排名并新增派单、最终调度快照、更新工单和写日志；失败全部回滚。
- **负载**：P0 使用数据库查询未结束有效任务数，不采用可能失真的前端缓存值作为唯一判断依据。人员容量在事务中再次核查。
- **SQLite 并发**：开启外键约束，设置合理 `busy_timeout`；按需要开启 WAL；读写事务边界必须清楚。不要把 SQLite 当作高并发生产数据库。
- **验收/转派**：验收通过结束有效派单并释放负载；维修提交使未决转派申请 `SUPERSEDED`；相关状态、日志和派单/申请更新必须同事务提交。
- **评价**：为每工单唯一有效评价添加数据库唯一约束并在应用层处理重复请求。
- **删除**：工单和状态日志禁止物理删除；附件可执行受控逻辑删除或延迟清理。

## 48.3 建议 ER 关系

用户 1:N 工单；用户 1:0..1 维修档案；维修员 M:N 技能；工单 1:N 附件；工单 1:N 派单历史；工单 1:N 状态历史；工单 1:N 调度记录；工单 1:0..1 有效评价。位置与分类由工单通过外键关联。

# 49. API 契约与错误语义（新增）

# 50. 智能调度的可检验算法规范（新增）

## 50.1 两段式设计

**先排序工单，再为每张工单排序人员**。工单优先级决定处理顺序；人员综合评分决定该工单推荐谁。不能把“紧急工单优先”简单理解为给所有维修员额外加固定分。

P0 不依赖机器学习训练，也不依赖外部付费 AI API；核心算法用纯 C++ 实现，独立可测试。

## 50.2 候选过滤

对每位维修人员依次验证：有效账户、可用状态、所需技能（及必需资质）、负责区域或明确授权跨区、当前有效任务数 < 最大并行数。任一条件不满足，拒绝进入推荐名单并记录排除原因。P0 只在当前时刻计算可用性，排班时段约束作为 P1。

## 50.3 打分规则

与第 14.5 节相同，默认权重：技能 0.35、区域 0.20、负载 0.20、历史效率 0.10、服务评价 0.10、紧急值班 0.05。**所有原始指标都规范到 0～100**。

`score = 0.35*skill + 0.20*area + 0.20*load + 0.10*efficiency + 0.10*rating + 0.05*duty`。

- 技能评分：所需技能熟练度为 1～5，可采用 `level/5 * 100`；未取得必需资质者在过滤阶段剔除。
- 区域评分：同楼宇 100、同校区其他楼宇 70、获准跨区 30；P0 不依赖真实地图距离。
- 负载评分：`100 * (1 - active_tasks / max_tasks)`，裁剪到 `[0,100]`；`max_tasks<=0` 视为不可用。
- 历史效率：有效样本为该维修员最近 20 个以 `COMPLETED` 正常结束、具有 `accepted_at` 和最终 `result_submitted_at` 的派单。`actual_minutes=max(1, accepted_at 到最终结果提交的分钟数)`；单样本 `efficiency_sample=clamp(100×fault_categories.target_completion_minutes/actual_minutes,0,100)`。有效样本少于 3 个取 60，否则取算术平均并四舍五入到 1 位小数。返工时使用最后一次结果提交时间，全部尝试仍由日志保留。
- 服务评价：取该维修员最终完成工单最近 20 条有效评价，单项 1～5 星先以 `score×20` 映射到 0～100；有效样本少于 3 个取 60，否则取算术平均并四舍五入到 1 位小数。
- 紧急值班：紧急工单且人员为值班者记 100；否则记 0。普通工单也可保持该权重项为 0，所有人的分数可比。
- 同分排序：按负载更低 → 人员编号升序，保证结果可复现。

**权重与阈值均为待测试参数**，不是现实中验证过的最优调度公式。P0 固定权重；P1 提供管理界面配置，配置需校验总和为 1，并存快照。

## 50.4 推荐结果契约

返回 `top_candidates`（最多 3 人）、`other_eligible_candidates`、分项分、理由、风险、样本量和 `excluded_summary`。推荐动作只计算，不修改工单且不写 `dispatch_records`。管理员确认派单时重新计算硬约束、负载与排名；选择非 Top 3 时理由必填，并在同一事务保存最终推荐依据/权重快照、选中人员、派单、状态和日志。

## 50.5 可比较的实验

准备至少 5 组种子数据：①普通工单多人合格；②紧急工单值班人员加分；③技能不匹配；④负载达到上限；⑤综合得分相同。分别记录候选列表、分项得分、推荐理由、结果是否稳定，并与“最小负载优先”规则基线比较。不声称算法优于人工或其他方法，除非有量化实测。

# 54. 测试数据与演示故事板（新增）

建议初始化：1 名系统管理员、1 名调度管理员、3 名报修人、6 名维修人员；3 个故障技能（电、水、网络）及交叉技能；2 个校区、至少 4 栋建筑；15～30 张处于不同状态的虚拟工单。不要使用真实学生个人信息。

**10 分钟主线演示：**

1. 报修人登录并提交“宿舍插座故障”，上传虚拟图片 → 看到工单编号。
2. 调度员审核并确认“电气类” → 进入待派单。
3. 打开调度候选 → 比较三位维修员的技能、区域、负载和评分，确认推荐人。
4. 维修员登录 → 接单 → 填写维修结果。
5. 报修人登录 → 查看时间线、验收、评价。
6. 调度员关闭工单 → 看板数字更新，并展示历史日志。
7. 演示“某维修员满负载/技能不匹配被过滤”及“重复派单被拒绝”两个异常，突出 C++ 算法与并发控制。

# 55. 研发规范与 AI 辅助约束（新增）

- 提交源代码前必须本地编译及测试；AI 输出未执行时标注“未验证”。
- UI 组件不直接访问数据库；Controller 只解析请求/返回响应；Service 管业务流程；Repository 处理持久化；DispatchStrategy 只做计算。
- 任务一次修改一个模块；先给出变更文件列表，再编码，最后运行测试并解释错误。
- 禁止让 AI 大范围重写已通过测试的模块，或无理由增加依赖。
- 代码和需求使用同一 FR 编号；Git 提交信息标注编号，如 `feat(FR-007): implement dispatch scoring`。
- 编码先写边界测试，再修改实现；调度算法用固定种子数据检验相同输入返回稳定结果。
- `docs/decisions.md` 记录每次架构与需求决策：问题、选项、最终选择、原因、影响。
