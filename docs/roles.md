# CampusFix 四角色权限与数据范围矩阵

> **版本**：V1.0（W1-D5 P0 冻结基线）
> **依据**：`docs/SRS.md` 第 46、47 章，`docs/requirements-trace.md` 的 FR-002～FR-013，以及 `docs/flows.md`。
> **说明**：本文定义授权规则和预期验收，不代表鉴权代码已经实现。

## 1. 权限模型

授权必须同时满足两个独立维度：

1. **动作权限**：当前角色是否可以发起该类操作。
2. **数据范围**：该用户是否对目标工单、附件、人员或统计范围具有资源级权限。

前端隐藏按钮只是体验优化，不能替代后端检查。服务器还必须校验登录状态、工单状态、当前有效派单、管辖区域和版本。路径参数、请求体中的 `reporter_id`、`operator_id`、角色、负责人和目标状态均不可直接信任。

角色代码固定为：`reporter`、`worker`、`dispatcher`、`sysadmin`。P0 每个账户只设置一个主要角色，不提供复杂角色切换；`worker` 具有为本人报修的特例权限，但这不改变其主要角色，也不授予其访问他人报修数据的权限。管理员代报和复杂多角色账户属于 P1。

## 2. 操作权限矩阵

图例：**允许**表示还需满足状态与数据范围；**受限**表示仅在特别说明的本人身份/范围内允许；**明确授权**表示不能从 `sysadmin` 角色自动获得，必须另行授予具体业务能力；**禁止**表示该角色不能执行该业务动作。

| 功能 / 动作 | `reporter` | `worker` | `dispatcher` | `sysadmin` | 资源与状态限制 |
|---|---|---|---|---|---|
| 创建报修 | 允许 | 受限 | 禁止 | 禁止 | `reporter` 或 `worker` 只能以本人作为报修人；管理员代报为 P1 |
| 编辑草稿/待补充内容 | 允许 | 受限 | 禁止 | 禁止 | 仅原报修人的 `DRAFT` / `PENDING_SUPPLEMENT` |
| 提交/补充后再提交 | 允许 | 受限 | 禁止 | 禁止 | 仅原报修人；服务器决定目标状态 |
| 取消早期工单 | 允许 | 受限 | 允许 | 明确授权 | 原报修人或明确授权管理人员；原因规则见 `flows.md` T-07～T-12 |
| 查看工单列表/详情 | 允许 | 允许 | 允许 | 明确授权 | 必须按第 3 节过滤数据范围 |
| 审核通过/退回/拒绝 | 禁止 | 禁止 | 允许 | 明确授权 | `dispatcher` 仅管辖区域；授权不能绕过状态和审计 |
| 查看调度候选 | 禁止 | 禁止 | 允许 | 明确授权 | 工单在授权范围且为 `PENDING_DISPATCH`；只读、不派单 |
| 确认派单/改派审批 | 禁止 | 禁止 | 允许 | 明确授权 | 不得绕过技能、资质、在岗、区域和容量硬约束 |
| 接单 | 禁止 | 允许 | 禁止 | 禁止 | 仅当前有效负责人且为 `PENDING_ACCEPT` |
| 拒单 | 禁止 | 允许 | 禁止 | 禁止 | 仅当前有效负责人；原因必填 |
| 申请转派 | 禁止 | 允许 | 禁止 | 禁止 | 仅当前有效负责人；申请本身不改变状态/负责人 |
| 记录到场/维修进度 | 禁止 | 允许 | 禁止 | 禁止 | 仅当前有效负责人且工单为 `IN_PROGRESS`；属于 E-01/E-02 事件，不改变状态 |
| 提交维修结果 | 禁止 | 允许 | 禁止 | 禁止 | 仅当前有效负责人且为 `IN_PROGRESS` |
| 验收通过/返工 | 允许 | 禁止 | 禁止 | 禁止 | 仅原报修人且为 `PENDING_VERIFY`；管理员不得代验收 |
| 评价 | 允许 | 禁止 | 禁止 | 禁止 | 仅原报修人、`COMPLETED`、每单最多一次 |
| 归档关闭 | 禁止 | 禁止 | 允许 | 明确授权 | 授权范围内 `COMPLETED`；评价不是关闭前置，关闭后不可补评 |
| 上传图片附件 | 允许 | 受限 | 禁止 | 禁止 | 原报修人上传 REPORT；当前负责人在 IN_PROGRESS 上传 REPAIR_RESULT；两类分别最多 3 张 |
| 下载附件 | 允许 | 允许 | 允许 | 明确授权 | 继承关联工单的数据范围；禁止仅凭附件 ID 下载 |
| 查看公开时间线 | 允许 | 允许 | 允许 | 明确授权 | 继承工单可见范围；字段按受众过滤 |
| 查看内部审核/调度备注 | 禁止 | 禁止 | 允许 | 明确授权 | 仅授权管理人员可见；严格使用第 4 节字段白名单 |
| 维护维修人员技能/容量 | 禁止 | 只读本人 | 允许 | 明确授权 | `dispatcher` 仅负责区域；`sysadmin` 仅明确授权范围 |
| 查看管理统计 | 禁止 | 禁止 | 允许 | 明确授权 | `dispatcher` 仅管辖区域；`sysadmin` 仅明确授权范围 |
| 管理账户/系统配置 | 禁止 | 禁止 | 禁止 | P1 | P0 不提供通用管理 API/UI；初始化数据也不授予业务冒名权限 |

表中 `worker` 的“受限创建/提交/取消”是 P0 明确的本人报修特例，不需要切换主要角色；它只能处理本人创建的工单，不能访问他人报修数据。

## 3. 各角色数据范围

### 3.1 `reporter` 报修人

- 只能列出、查看、补充、取消、验收和评价 `reporter_id` 为本人的工单。
- 可查看本人有权访问工单的公开时间线和附件；不能查看内部审核意见、候选人完整评分、任何内部审核/调度备注或他人工单。
- 即使知道他人工单 ID、时间线 ID 或附件 ID，也不得获取资源内容或推断敏感信息。

### 3.2 `worker` 维修人员

- 可查看当前有效分配给本人的工单，以及为追溯本人历史任务所需的受控历史记录。
- 只有当前有效负责人能接单、拒单、申请转派和提交维修结果；原派单结束后，旧负责人立即失去后续操作权。
- 可查看完成任务所需的位置、故障、公开历史和附件；不得读取内部审核/调度备注或其他维修员任务。
- 可使用本人账户创建、补充、提交和取消本人报修，但该特例不扩大维修任务数据范围。
- 可只读查看本人技能、资格、在岗与容量资料，不能自行提升资质或容量。

### 3.3 `dispatcher` 调度管理员

- 仅能查看和操作授权校区/区域内的工单、人员和统计数据。
- 可审核、查看推荐、确认派单、审批转派、取消待派单工单和关闭已完成工单；所有动作还需满足状态、版本与硬约束。
- 可查看管辖范围内的内部审核/调度信息，但不能冒充维修员接单/提交结果，也不能代替报修人验收/评价。

### 3.4 `sysadmin` 系统管理员

- 仅能按明确授予的系统管理权限查看或维护账户、配置、审计数据、人员资料和统计；`sysadmin` 角色本身不等于全局业务数据通行证。
- SRS 中“授权管理”不等于天然拥有调度业务权限；查看业务数据、审核、派单、取消或关闭均须明确授予对应能力和范围，并留下本人审计记录。
- 始终不能冒名接单、提交维修结果、验收或评价。紧急修复数据也不能绕过状态机和审计流程。

### 3.5 P0 管理能力码与范围

`sysadmin` 的业务授权以及需要细分的管理授权使用下列固定能力码；角色本身不隐含任何一项。`dispatcher` 由角色取得表中管理动作、由 `AREA_SCOPE` 限定区域；`sysadmin` 必须拥有动作能力记录，其 `scope_location_id` 直接限定区域（NULL 才表示该能力全局），`AREA_SCOPE` 单独存在不授予动作：

| 能力码 | 允许动作 | 仍须满足的范围/业务条件 |
|---|---|---|
| `BUSINESS_READ` | 读取工单、公共时间线与获准附件 | sysadmin 以本能力记录的 `scope_location_id` 限定范围 |
| `REVIEW` | 审核通过、退回、拒绝 | 管辖区域、状态和版本校验 |
| `DISPATCH` | 推荐、初次派单、审批维修员转派申请 | 管辖区域、硬约束和状态校验；不含 P0 主动改派 |
| `CANCEL` | 管理员取消允许状态的工单 | 管辖区域、原因和版本校验 |
| `CLOSE` | 关闭 `COMPLETED` 工单 | 管辖区域和版本校验 |
| `WORKER_MANAGE` | 维护技能、资格、在岗和容量 | 授权区域内维修员 |
| `STATS_VIEW` | 查看管理统计 | 仅授权区域/全局范围 |
| `INTERNAL_NOTE_READ` | 读取白名单内的内部审计字段 | 还需具备目标工单的业务读取范围 |
| `AREA_SCOPE` | 表达 dispatcher 的管辖区域，也可用于授权摘要 | 本身不是业务动作；不能替代 sysadmin 的动作能力记录 |

P0 不提供权限管理 UI 或通用账户管理 API；能力与范围由种子数据/受控初始化配置。`SYSTEM_MANAGE` 不属于本期业务能力码。

## 4. 信息可见性分层

| 信息类别 | 报修人 | 当前维修员 | 调度管理员 | 系统管理员 |
|---|---|---|---|---|
| 工单公开字段、当前状态 | 本人工单 | 本人任务 | 管辖区域 | 仅明确授权范围 |
| 公开时间线 | 本人工单 | 本人任务 | 管辖区域 | 仅明确授权范围 |
| 报修附件/维修结果附件 | 按工单权限 | 按本人任务权限 | 管辖区域 | 仅明确授权范围 |
| 退回给报修人的原因 | 可见 | 完成任务所需时可见 | 可见 | 仅明确授权范围可见 |
| 内部审核备注 | 不可见 | 不可见 | 管辖区域可见 | 仅明确授权范围可见 |
| 完整候选评分与排除原因 | 不可见 | 不可见 | 管辖区域可见 | 仅明确授权范围可见 |
| 派单/转派内部理由 | 只显示必要公开结论 | 只显示完成任务所需的公开结论 | 管辖区域可见 | 仅明确授权范围可见 |
| 个人敏感信息/凭证 | 不返回 | 不返回 | 不返回 | 仅在明确授权下返回最小必要管理信息；永不返回密码/完整 Token |

后续 API 必须针对受众构造响应，不能先返回完整对象再依赖前端隐藏字段。冻结的返回白名单如下：

- 公共时间线：`id`、`action`、`from_status`、`to_status`、`public_note`、`actor{id,display_name}`、`created_at`，以及当前用户获准访问的附件摘要。
- 授权管理扩展：`internal_note`；并按事件类型仅增加 `review_action/category_id/approved_urgency`、`assignment_id/worker_id/assign_reason/candidate_rank`、`transfer_request_id/decision`、`rework_count` 中适用的字段。
- 所有角色均不得从业务响应获得原始 `metadata_json`、密码/Token、附件 `stored_path` 或无关人员联系方式。

## 5. 服务器鉴权顺序

每个受保护请求至少按以下顺序判断：

1. **认证**：会话是否存在、有效、未撤销；失败通常为 401。
2. **动作权限**：当前角色是否允许发起该动作；失败为 403，或在需要隐藏资源存在性时为 404。
3. **资源范围**：是否为原报修人、当前有效负责人、管辖区域管理员或全局授权管理员。
4. **业务前置**：当前状态、必要原因/字段、技能/资质/在岗/区域/容量是否满足。
5. **并发校验**：版本和有效派单是否仍与读取时一致；冲突通常为 409。
6. **原子写入与响应过滤**：事务提交状态、派单和日志；响应只包含该角色可见字段。

401/403/404/409/422 的具体业务码、资源隐藏策略和端点契约将在 W1-D4 统一定义，本稿不提前冻结接口形式。

| `RBAC-D3-12` | 未获相应授权的 `sysadmin` 尝试读取内部备注或执行审核、派单、关闭 | 拒绝；系统管理员角色本身不授予业务数据或操作权限 |

## 7. W1-D5 冻结结论

- P0 每个账户只有一个主要角色；`worker` 可为本人报修，管理员代报与复杂多角色切换属于 P1。
- `sysadmin` 不天然拥有调度、接单、维修、验收等业务权限；具体管理能力必须明确授权。接单、维修、验收和评价仍受当前负责人/原报修人身份约束，不能冒名。
- 内部审核和调度备注只对授权管理人员可见；字段白名单已由第 4 节和 API 契约冻结。
- `COMPLETED` 可不经评价直接关闭；`CLOSED` 后不再接受评价。
- P0 仅允许审批维修员发起的转派申请；管理员无申请主动改派属于 P1。
- 上述规则已在 W1-D5 冻结；实现与测试状态仍须在后续阶段按证据更新。
