# CampusFix——校园维修工单与智能调度系统

## 10 周开发实施计划 V1.0（单人 + AI 协作）

> 对应需求基线：《CampusFix_需求规格说明书_V1.1_完善版.md》。原始选题技术路线：C++ / Drogon REST API + Vue3 / Element Plus / Axios / ECharts；起步数据库 SQLite。**不是 Qt 桌面版。**
>
> 项目性质：课程设计、工程实践；建议每周稳定安排约 8～12 小时，10 周为基准、允许延长到 12 周。不承诺该工时适合所有初学者。所有演示用数据均为虚构。
>
> 本计划将“需求完成”定义为：后端业务可执行 → 相关 API 有验证 → 前端可操作 → 关键失败场景有处理 → 测试记录可追踪 → Git 有稳定提交。

---

# 0. 首先遵守的开发原则

1. **先主流程，后高阶功能**：从最小可运行 Web 页面开始，逐步形成报修→审核→推荐→派单→接单→完工→验收→评价→关闭的闭环。
2. **不要一次让 AI 生成全项目**：一次任务只覆盖一个模块、一组接口或一段前端流程。
3. **后端始终是权限和状态的最终裁判**：前端传的用户 ID、状态、负载不可直接信任。
4. **调度算法分为“纯计算”和“提交派单”**：前者不改数据库，后者必须有事务和冲突处理。
5. **以需求 ID 做追踪**：每个任务标记 FR、实现文件、测试编号和 Git 提交。
6. **每个工作日结束后确保主分支能运行**：AI 更改前先提交或创建分支，改后做回归测试。

## 0.1 P0/P1/P2 分界

- **P0 必做**：身份与四角色权限、真实工单业务闭环、必要附件、维修人员技能与负载、可解释智能推荐/人工派单、基础统计、历史日志、可运行可测试的 Web 系统。
- **P1 有余力再做**：人员排班、超时预警、权重配置、多策略比较、工单导出、站内通知、Docker Compose、压力测试指标。
- **P2 暂不做**：大模型/图像识别自动分级、学校统一身份认证、真实地理路线、微信小程序、短信、自动验收、机器学习训练。

# 2. 从第 1 天开始的明确任务列表

**第一天不要编写登录页面。**先做：

1. 建立本地文件夹 `CampusFix` 和 Git 仓库，写 `README.md`：项目目标、技术栈、开发方式。
2. 复制需求 V1.1 到 `docs/SRS.md`，将其中的 P0 标记为本期范围。
3. 在 `docs/decisions.md` 确定默认方案：Drogon + Vue3 + SQLite、四角色、管理端人工确认派单、P0 不超负载派单。
4. 建 `docs/flows.md`：画出普通、退回补充、拒单重派、验收不通过四条流程。
5. 用一张业务用例检查表确认你能解释：谁点什么按钮、后端改什么状态、数据库新增什么记录。
6. 提交 `git commit -m "docs: initialize CampusFix requirements baseline"`。

**第一天验收**：可打开仓库；阅读需求书时清楚知道 MVP 边界；不再讨论 Qt 或 Web 的路线摇摆。

# 4. 逐周详细任务（按 5 个学习/开发单元组织，可根据课表调整）

| W1-D2 | 逐项审阅 FR-001～FR-015；给每项写业务前提、触发、结果、错误场景、验收 | requirements-trace.md | 每一项 P0 都能设计出至少 1 个测试 |
| W1-D3 | 画工单状态机；处理拒单、转派、验收失败、取消；绘制权限矩阵 | flows.md、roles.md | 找不到没有定义的状态跳转 |
| W1-D4 | 数据实体关系/字段草案；HTTP API 清单、权限、参数；前端页面线框 | database-design.md、api-contract.md、ui-wireframes.md | 页面按钮与 API 操作能一一对应 |

**本周必须判断**：工单是不是 DRAFT 默认创建？本版可采用 `POST /work-orders` 创建草稿、`POST /submit` 正式提交；若为了简化决定直接创建即提交，必须同步改 SRS/API/测试三处。本计划默认采用前者，以保持原需求一致。

**给 AI 的任务模板**：

```text
你是软件需求分析师。请审阅本项目 docs/SRS.md 的 FR-001 到 FR-013。
不能改变 C++/Drogon + Vue3 技术路线。
把每条需求转为：角色、前置条件、触发动作、输入、正常结果、异常结果、验收测试。
重点检查工单状态冲突、越权和重复派单，不要写代码。输出可直接存入 docs/requirements-trace.md。
```

**W1 交付**：项目设计文档第一版；所有 P0 的范围明确。

## W6：智能调度（核心展示周，建议 12～16 小时）

| 单元 | 具体要做什么 | 产出 | 自检 |
|---|---|---|---|
| W6-D1 | 定义纯 C++ WorkOrder/Worker/Candidate 类型与 `DispatchStrategy` 接口 | DispatchStrategy、模型、单测 | 给固定输入得到固定输出 |
| W6-D2 | 硬筛选：状态、技能/资质、服务区域、人员最大任务容量；输出排除原因 | EligibilityFilter | 不合格人员绝不能出现在前三名 |
| W6-D3 | 实现技能、区域、负载、历史效率、评价、紧急值班分项评分；排序及推荐解释 | WeightedScoreStrategy | 分数可复算、同分次序稳定 |
| W6-D4 | 实现推荐 API + 记录快照；派单事务、version 冲突、有效任务数二次确认 | DispatchService、AssignmentService | 两个管理员竞争派单，只能一次成功 |
| W6-D5 | 开发调度面板：前三名、评分细节、拒绝原因、确认/人工改派；写测试 | DispatchView、TC-DSP-01～08、TC-CON-01～03 | 从 PENDING_DISPATCH 真实变为 PENDING_ACCEPT |

**核心边界**：推荐≠自动派单。`GET candidates` 只能计算和返回候选，不应该修改负责人；`POST assign` 才完成交易。对于多张工单，P1 可进一步用 `std::priority_queue` 实现优先级待办队列、增加策略切换展示；P0 优先把单张工单的推荐做对。

**建议实验数据**：普通工单、紧急值班、技能不匹配、容量为零、同分候选、无候选共 6 组。每组记录 `输入→过滤→评分→排序→理由`，不夸大算法准确率。

## W7：维修业务闭环（约 10～14 小时）

| 单元 | 具体要做什么 | 产出 | 自检 |
|---|---|---|---|
| W7-D1 | 维修员只对当前自己的 PENDING_ACCEPT 任务接单、拒单并写原因 | Accept/Refuse APIs、WorkerTasks | 拒单后回到 PENDING_DISPATCH，负载释放 |
| W7-D2 | 转派申请/管理员确认；旧派单记录完结，新负责人重新推荐 | TransferService、transfer UI | 历史负责人和原因保留 |
| W7-D3 | 维修员填写维修过程与结果，转 PENDING_VERIFY；时间线更新 | Complete API、Progress UI | 无完成说明不可提交 |
| W7-D4 | 报修人验收通过→COMPLETED，未通过→IN_PROGRESS（返工） | Verify API、Verify UI | 只有原报修人能验收，退回原因保留 |
| W7-D5 | 一次性评价、管理员关闭、流程端到端测试 | EvaluationService、Close API、E2E 场景 | 完整工单从提交到 CLOSED 无人工修改 DB |

**本周是成败门槛**：若 W7 尚不能从学生到维修再到学生完成一单，暂停新功能，专门修业务闭环。

# 5. 每一阶段为什么按这个顺序做

```text
需求 / 状态 / 权限
          ↓
       环境能跑
          ↓
  数据库 + 登录 + 鉴权
          ↓
       报修 CRUD
          ↓
   审核与人员技能数据
          ↓
       调度与派单
          ↓
     维修、验收与评价
          ↓
    附件 + 统计 + 美化
          ↓
    测试、部署、答辩
```

调度模块依赖工单数据、人员技能和负载，因此必须排在 W4/W5 后。评价依赖完工验收，不应该在第 2 周先做。界面美化不能替代真实后端接口。安全与自动化测试从 W3 起就持续执行，W9 是集中补充而不是第一次测试。

# 7. 适用于 AI 编程助手的固定协作流程

## 7.1 每次编码采用 6 步

1. **提供上下文**：对应 SRS 章节、API 契约、目前相关源代码、错误日志。
2. **要求先列方案**：AI 先写需新增/修改文件、类和测试点，暂不改代码。
3. **小范围实现**：只改目标模块，禁止无理由动数据库和公共 API。
4. **本地验证**：编译、运行、实际发送 HTTP 请求、查看数据库。
5. **让 AI 查漏补缺**：输入真实失败日志，要求说明根因和最小修改。
6. **合并与归档**：测试通过后 Git 提交，并更新需求追踪表。

# 8. 推荐的 Git 工作流（适合一个人）

- `main`：只放本周已验证、随时可演示的版本。
- `feature/<FR编号>-<简短描述>`：一个功能一个分支，例如 `feature/fr-007-dispatch`。
- 提交之前：执行编译、目标模块测试和简短 smoke test；确保 secrets、数据库文件、真实上传文件没提交。
- 每周末打标签：`w2-skeleton`、`w4-reporting`、`w6-dispatch`、`w7-closed-loop`、`v1.0.0`。
- 故障无法解决时：回到上一个可运行提交，不让 AI 在一团混乱中持续打补丁。

## 10.2 可能遇到的风险和解决顺序

| 风险 | 征兆 | 立即采取的动作 |
|---|---|---|
| Drogon 构建环境反复失败 | W2 超过预期仍编译不通 | 固定操作系统/编译器/依赖版本；只保留 `/health`；逐条解决首个错误 |
| AI 改动造成前后端接口混乱 | JSON 字段、状态命名不一致 | 回滚本次变更，以 api-contract.md 为唯一契约 |
| 需求持续膨胀 | 新页面不断增加、W4 主流程仍不通 | 冻结 P0，暂停 P1/P2；每周只追求可运行纵向切片 |
| SQLite 并发异常 | 派单出现 database locked 或重复负责人 | 缩小事务、busy_timeout/WAL、条件更新、并发回归测试；不要靠前端按钮禁用保证一致性 |
| 前端好看但业务不通 | 用假数据演示，API 未联通 | 暂停 UI 美化，用真实接口贯穿一张工单 |
| 学习成本过高 | 单周技术栈太多 | 减少高阶通知、动态配置、复杂文件系统、Docker，保留 C++ 调度和核心闭环 |
| 临近答辩不稳定 | 一改代码就破坏已有流程 | W9 后禁止新功能，锁定发布分支，只修阻塞缺陷 |

## 10.3 只剩 6 周怎么办（应急 MVP）

第 1 周：需求、环境；第 2 周：登录和数据库；第 3 周：报修与审核；第 4 周：C++ 调度与事务派单；第 5 周：接单→验收→评价；第 6 周：测试、看板、交付。删掉排班、多策略、站内通知、复杂统计、自动验收、Docker；图片上传也可以从多图收敛为单图，但必须修改需求说明和验收文件明确范围。**不能删除服务端权限、有效派单唯一性和核心状态校验。**
